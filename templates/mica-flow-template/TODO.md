## Goals board integration

Flows should systematically update goals instead of us hand-maintaining them:

- **Scaffold from a goal:** `mica-flow new --from-goal <goal-id>` reads the goal's
  `GOAL.md`, proposes cycles from its open items, and links the flow back.
  The flow's `AGENT.md` frontmatter gets `goal: <goal-id>`.
- **Status pushes to goals:** `mica-flow-status` (or a `--sync-goal` flag) writes
  cycle completions into the goal's activity log. When all cycles hit `done`,
  propose closing or advancing the goal — don't auto-close, surface it.
- **Subgoals as cycles:** a goal with subgoals maps 1:1 to flow cycles.
  `mica-flow-status` could render subgoal checkoffs. We've hardly kept subgoals
  current — this would make them self-maintaining.
- **Bidirectional:** goal board shows linked flow + live status (read from
  `cycle.md` frontmatter, no duplication).

## Automation OSS

Existing pieces we could wire in (names TBD — Curtis to confirm):

- **DBOS** (durable workflows, already in `~/workspace/reference/dbos.md`):
  a flow cycle could *be* a DBOS workflow for crash-safe multi-step work.
  The `_run/` folder maps naturally to DBOS's event log.
- **n8n-like triggers:** a cycle's gate could be an external webhook
  (e.g. "advance when CI passes"). `mica-flow-status --watch` as a lightweight
  poller, or a hook that wakes the router.
- **Windmill / Flowise** (future UI layer per Curtis): flows already have the
  structure (cycles, gates, briefs) — a UI could render `mica-flow-status`
  output directly. No new schema needed.
